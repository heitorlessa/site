Every public API needs a way to say "slow down." The **token bucket** is the
classic answer: simple to build, cheap to run, and it behaves the way people
actually want — a little burst is fine, but the long-run average is capped.

Here's the whole idea in one sentence: **you need a token to act, tokens refill
at a steady rate, and the bucket only holds so many.**

## The refill loop

The bucket refills on a clock, independent of traffic. Watch the cycle: tokens
drip in, requests spend them, and when the bucket is empty, requests wait.

Two numbers define the policy:

- **Rate** — how fast tokens refill (the sustained request rate you allow).
- **Capacity** — how many tokens the bucket holds (the size of a burst you tolerate).

A big capacity forgives spikes; a small one keeps traffic smooth. Rate sets the
long-run average no matter what.

## What a client sees

When the bucket runs dry, a good API doesn't just fail — it tells the client
*when* to try again. Step through a client that hits the limit and backs off.

## In code

The elegant part: you don't need a background timer. Compute the refill lazily
from elapsed time whenever a request arrives.

```ts
class TokenBucket {
  private tokens: number;
  private last = Date.now();

  constructor(
    private capacity: number,
    private ratePerSec: number,
  ) {
    this.tokens = capacity;
  }

  tryRemove(cost = 1): boolean {
    const now = Date.now();
    // Refill based on how much time has passed — no timer needed.
    this.tokens = Math.min(
      this.capacity,
      this.tokens + ((now - this.last) / 1000) * this.ratePerSec,
    );
    this.last = now;

    if (this.tokens >= cost) {
      this.tokens -= cost;
      return true; // allowed
    }
    return false; // rate limited → return 429
  }
}
```

That "refill from elapsed time" trick is why the token bucket scales: state is
two numbers per client, and there are no timers to manage.

## Why not just count requests per minute?

A fixed window ("100 requests per minute") has an ugly edge: a client can send
100 at 11:00:59 and 100 more at 11:01:00 — 200 requests in one second, all
"within limits." The token bucket has no such seam. It smooths naturally,
because refill is continuous, not stepped.

Reach for the token bucket first. It's the rate limiter that behaves the way you
meant.
